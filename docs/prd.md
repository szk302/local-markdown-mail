## 1. システム概要

### 1.1. 目的

LMM は、ローカルのファイルシステムだけを使って、AI エージェントと人の間で Markdown メッセージをやり取りする CLI である。tmux などの端末環境には依存しない。新着の通知は、AI CLI のフックから `lmm hook` を呼ぶ方式（pull 型）で行う。

### 1.2. 設計原則

* **ファイルシステムをキューとする:** データベース、メッセージブローカー、常駐プロセスを使わない。
* **人がそのまま追える:** メールボックス、原本、状態は、`ls` と `cat` だけで追える形で持つ。データベースや索引ファイルは、中身を見るのに専用の道具が必要になり、パッと見で追えなくなるため使わない。
* **メールは中央で管理する:** すべてのメールボックスを 1 つのデータディレクトリ（`~/.lmm`）に置く。ワークツリーを削除してもメールは失われない。
* **切り替えは `rename` 1 回で行う:** 配送、受信、送信控えの保存、メールボックスの作成・削除では、準備を終えたディレクトリを `rename` 1 回で切り替える。データディレクトリ内の移動はすべて同じファイルシステム上で行うため、途中で停止しても中途半端な状態は見えず、作業記録や再開の手順を必要としない。
* **メッセージはディレクトリとする:** 本文 `index.md` と添付ファイルを 1 つのディレクトリにまとめ、一体として扱う。
* **状態はファイルシステムで持つ:** 展開済みかどうかは、メッセージの置き場所（`new/` か `cur/` か）で表す。ディレクトリ名は Maildir に倣う。
* **人間とエージェントの双方が読める形式:** メッセージは YAML フロントマター付きの Markdown とする。

### 1.3. 用語

| 用語 | 意味 |
| :--- | :--- |
| データディレクトリ | すべてのメールボックスと設定を置くディレクトリ（§4.1）。 |
| アドレス | メールボックスの識別子。送信元・宛先を表す。 |
| メールボックス | アドレスごとのディレクトリ。inbox と sent を持つ。 |
| メッセージディレクトリ | 1 通のメッセージ。`index.md` と添付ファイルを含む（§5）。 |
| 展開先 | `lmm receive` がメッセージをコピーするディレクトリ（§7.2）。 |
| 展開済み | 展開先へのコピーを終え、原本を `inbox/cur/` へ移した状態。通知済みであることは意味しない（§8.5）。 |

## 2. 構成

```
[送信者]                     ~/.lmm/boxes/<宛先>/                       [受信者]
 lmm post ──(rename)──► inbox/new/<msg>/ ─┐
                                          │  lmm receive / lmm hook
                                          ├──(コピー)──► <展開先>/<msg>/ ──► エージェントが読む
                                          └──(rename)──► inbox/cur/<msg>/（原本として残る）
```

常駐プロセスはない。すべての処理はコマンドの実行時に完結する。配送できない場合（宛先のメールボックスがない場合）は、送信時にエラーとする。配送の保留、再試行、配送不能メッセージの隔離は行わない。

## 3. アドレスと参加者

### 3.1. アドレス
* 使用可能な文字は `a-z 0-9 . _ -` とし、先頭の文字は `a-z 0-9` のいずれかとする。長さは 1〜64 文字とする。
    * `.` で始まる名前（`.` と `..` を含む）を禁止するのは、`boxes/.` や `boxes/..` がメールボックス以外の場所を指し、削除対象を取り違えるためである。また、`boxes/` 直下の `.` で始まる名前は、メールボックスの作成・削除の作業用に使う（§4.2）。
    * 大文字を禁止するのは、大文字と小文字を区別しないファイルシステム（macOS の既定など）で、`Alpha` と `alpha` が同じメールボックスを指すためである。
* アドレス `lmm` はシステムの予約とし、メールボックスには使えない。
* アドレスを受け取るすべての箇所で、上の規則を検証する。対象は、`lmm post -t`、返信元の `lmm_from`（§6.5）、設定の `post.reply_to`、`lmm box create` と `lmm box remove` の引数、`lmm wait --from`、受信時の検査（§7.3）である。規則に反する値は、何も作成せずにエラーとする。コマンドラインや設定の値は使い方の誤り・設定エラー（終了コード 2）、メッセージから読んだ値は実行時エラー（終了コード 1）とする。
    * アドレスはそのままパスの一部になるため、検証しないと、宛先の打ち間違いや壊れたメッセージによって、データディレクトリの外を指す（例: `../x`）。
* アドレスは、メールボックスが存在することで有効になる。メールボックスが存在するとは、`boxes/<アドレス>` がディレクトリとして存在することをいう。メールボックスは `lmm box create`（§9.1）で作成する。
* 役割名（例: `reviewer`）から実際のアドレス（例: `reviewer-042`）への対応付け（エイリアス）は設けない。対応表の更新や、並行するタスクで役割名がどのアドレスを指すかの管理が必要になるためである。役割で宛先を決めたい場合は、次の方法で対応する。
    * 返信は `lmm post --reply` を使う。宛先は受け取ったメッセージの `lmm_from` から決まる（§6.5）。
    * 決まった相手への報告は、設定の `post.reply_to`（§10.4）で宛先を決めておく。
    * `<役割>-<タスク ID>` のようなアドレスの命名規約を決め、送信者がアドレスを組み立てる。

### 3.2. 自分のアドレス
* コマンドを実行する参加者のアドレスは、環境変数 `LMM_NAME` だけで決める。設定ファイルでは指定できない。
* 階層型の設定（§10）にアドレスを書けると、同じディレクトリ配下で動くエージェントがすべて同じアドレスになってしまうためである。
* エージェントを起動するツール（tmac など）が、起動時に `LMM_NAME` を設定することを想定している。
* `LMM_NAME` が §3.1 の規則に反する場合は、使い方の誤り（終了コード 2）とする。ただし `lmm hook` では終了コード 1 とする（§8.3）。
* `LMM_NAME` が未設定の場合と、そのメールボックスが存在しない場合は、コマンドごとに次のとおりとする。

| コマンド | `LMM_NAME` が未設定 | メールボックスが存在しない |
| :--- | :--- | :--- |
| `lmm post` | 終了コード 2 | 終了コード 1（§6.4 の手順 1） |
| `lmm receive`、`lmm wait`、`lmm show --id` | 終了コード 2 | 終了コード 1。エラーメッセージで `lmm box create` を案内する |
| `lmm hook` | 何もせずに終了コード 0（§8.3） | 警告を出力して終了コード 0（§8.3） |
| `lmm draft` | 下書きの置き場に `{name}` を含む場合だけ終了コード 2（§6.7） | 影響しない |

* メールボックスの存在は、受信ロックを取得する前に確認する。存在しないアドレスのロックファイルを作らないためである。ロックを取得した後に、もう一度確認する（§4.3）。

## 4. データディレクトリ

### 4.1. 場所
* 環境変数 `LMM_HOME` が設定されていればその値、なければ `~/.lmm` とする。設定ファイルでは変更できない。
* データディレクトリ全体を 1 つのローカルファイルシステム上に置かなければならない（`rename` と `flock(2)` を使うため。NFS などのネットワークファイルシステムは対象外）。
* データディレクトリと `boxes/` は、存在しなければ `lmm box create` が作成する。

### 4.2. 構成

```
~/.lmm/
├── config.yml                    # グローバル設定（§10）
├── locks/                        # ロックファイル（§4.3）
│   ├── box/<アドレス>.lock
│   ├── receive/<アドレス>.lock
│   └── prepare/<アドレス>.lock
└── boxes/
    ├── .creating/                # 作成途中のメールボックス（§9.1）
    ├── .removing/                # 削除途中のメールボックス（§9.3）
    └── <アドレス>/
        ├── inbox/
        │   ├── .tmp/             # 配送と送信控えの書き込み途中（§6.4）
        │   │   └── <UUID>/       # 作業用ディレクトリ
        │   │       ├── lock      # 書き込み中を示すロックファイル
        │   │       └── msg/      # 書き込み中のメッセージディレクトリ
        │   ├── new/              # 未受信
        │   │   └── <メッセージディレクトリ>/
        │   ├── cur/              # 展開済み（原本）
        │   └── failed/           # 検査に合格しなかったメッセージ（§7.3）
        └── sent/                 # 送信控え
```

* `boxes/` 直下の `.` で始まるディレクトリは作業用であり、メールボックスではない。`lmm box list` などの対象にならない。

### 4.3. ロック
メールボックスごとに、`locks/` の 3 つのロックファイルに対する `flock(2)` のロックを用いる。

| ロック | ロックファイル | 保護するもの |
| :--- | :--- | :--- |
| メールボックス | `locks/box/<アドレス>.lock` | メールボックスの存在。配送と送信控えの公開と、メールボックスの作成・削除を調停する |
| 受信 | `locks/receive/<アドレス>.lock` | 受信処理。同時に実行されたフックと手動の受信が、同じメッセージを二重に展開するのを防ぐ |
| 準備 | `locks/prepare/<アドレス>.lock` | 作業用ディレクトリの準備（作成から、その `lock` のロックの取得まで、§6.4）。掃除が、準備中の送信を放棄されたものと取り違えるのを防ぐ |

このほか、送信の書き込み中であることを示すために、作業用ディレクトリの `lock`（§6.4）に対する `flock(2)` のロックを用いる。

| 処理 | 取得するロック |
| :--- | :--- |
| 配送と送信控えの書き込み（§6.4 の手順 4・6） | そのメールボックスの準備ロック（共有）→ 作業用ディレクトリの `lock`（排他）。準備ロックは `lock` のロックを取得したら解除し、`lock` のロックは作業用ディレクトリを削除するまで持ち続ける |
| 配送の公開（§6.4 の手順 5） | 宛先のメールボックスのロック（共有） |
| 送信控えの公開（§6.4 の手順 6） | 送信元のメールボックスのロック（共有） |
| 受信（§7.3） | 受信ロック（排他） |
| 放棄された作業用ディレクトリの掃除（§6.4。受信の中で行う） | 準備ロック（排他、待たない）→ 作業用ディレクトリの `lock`（排他、待たない） |
| `lmm box create`（§9.1） | メールボックスのロック（排他） |
| `lmm box remove`（§9.3） | 受信ロック（排他）→ メールボックスのロック（排他）→ 作業用ディレクトリの `lock`（排他、待たない） |

* ロックファイルはメールボックスの外（`locks/`）に置き、メールボックスを削除しても削除しない。ロックファイルを削除すると、待っていたプロセスと新しく取得したプロセスが別々のファイルをロックし、排他にならないためである。ロックファイルは存在しなければ作成する。
* ロックの種類ごとにディレクトリを分けるのは、ファイル名にアドレス以外の文字列を付けると、別のアドレスと衝突するためである（例: `alpha` の受信ロックを `alpha.receive.lock` とすると、アドレス `alpha.receive` のロックと同じファイルになる）。アドレスに `/` は使えないため、この配置では衝突しない。
* 配送どうしは共有ロックなので、同時に公開できる。準備ロックも送信どうしは共有なので、同時に準備できる。受信は別のロックを使うため、受信のコピーに時間がかかっても配送を待たせない。
* 複数のロックを持つ場合は、受信ロック → メールボックスのロックの順に取得する。準備ロックと作業用ディレクトリの `lock` は、この順序の制約に含めない。送信は、準備ロックを持っている間に、作成したばかりの `lock` のロックしか取得せず、それを待つことはない。掃除と `lmm box remove` は、準備ロックと `lock` のロックを待たずに取得する。そのため、デッドロックにならない。
* プロセスが終了するとロックは自動的に解除される。
* 待ち時間は最大 10 秒とし、取得できなければエラー（終了コード 1）とする。ただし、掃除が準備ロックを取得する場合と、送信以外が作業用ディレクトリの `lock` のロックを取得する場合は待たない（§6.4、§9.3）。
* 作業用ディレクトリの `lock` は、その作業用ディレクトリと一緒に削除する。上の「ロックファイルを削除しない」の例外であるのは、作業用ディレクトリの名前（UUID）を再利用せず、削除した後に同じロックファイルを取得しようとするプロセスがないためである。
* ロックを取得する前に確認した状態（メールボックスの有無など）は、判断に使う前に、ロックを持った状態で確認し直さなければならない。

## 5. メッセージ

### 5.1. メッセージディレクトリ
* 1 通のメッセージを 1 つのディレクトリとする。直下に本文 `index.md` を必ず置く。
    * `index.md` があるかは、ディレクトリの一覧に名前が完全に一致するファイルがあるかで判定する。ファイルを開けるかどうかでは判定しない。大文字と小文字を区別しないファイルシステムでは、`Index.md` しかなくても `index.md` として開けるため、`Index.md` を本文として読んだうえで、一覧では別の名前として添付ファイルにも数えてしまうためである。
* `index.md` 以外の通常ファイルは、すべて添付ファイルとする。添付ファイルの一覧をフロントマターに書く必要はない。
* サブディレクトリ、シンボリックリンク、その他の特殊ファイルを置いてはならない（リンク経由でディレクトリ外のファイルを渡せないようにするため）。
* ファイル名は、`/` と NUL を含まず、`.` で始まらない、255 バイト以下の名前とする。
* ファイル名は、ASCII の大文字と小文字を区別せずに比べて、互いに異なっていなければならない（`index.md` を含む）。例えば、`a.txt` と `A.txt`、`index.md` と `INDEX.MD` は同時に置けない。
    * 大文字と小文字を区別しないファイルシステム（macOS の既定や、それを Docker のバインドマウントでコンテナに見せた場合など）へコピーすると、2 つのファイルが同じファイルになり、後からコピーした内容で前の内容が上書きされるためである（アドレスで大文字を禁止したのと同じ理由、§3.1）。
    * この規則で防げない名前の同一視（ASCII 以外の文字の大文字と小文字、Unicode の正規化の違いなど）は、コピーの際の排他的な新規作成で検出する（§6.4、§7.3）。
* 本文からは、`./screen.png` のような相対パスで添付ファイルを参照できる。メッセージはディレクトリごと移動・コピーするため、参照は常に有効である。
* 1 通あたりの合計サイズ（`index.md` を含む）の上限は、設定の `max_message_size`（§10.4）とする。

例:
```
20261005-143005.123456_alpha_to_beta_a1b2c3d4/
├── index.md
└── screen.png
```

### 5.2. ディレクトリ名
視認性と時系列でのソートを容易にするため、ディレクトリ名は次のフォーマットに従う。

* **フォーマット:** `{YYYYMMDD-HHMMSS.ffffff}_{From}_to_{To}_{ShortID}`
    * 日時は `lmm_created_at` の値（UTC、マイクロ秒まで）を用いる。秒未満を含めるのは、同じ秒に作成したメッセージも、作成の順に並ぶようにするためである。
    * `ShortID` は `lmm_id` の先頭 8 文字とする。
* **例:** `20261005-143005.123456_alpha_to_beta_a1b2c3d4`
* 名前が重複する場合は、末尾に `_1`, `_2`, … を付ける（§6.4、§7.3）。
* ディレクトリの `rename` は、移動先に同じ名前があれば失敗する方法（上書きしない `rename`。実装は付録 A）で行う。通常の `rename` は、移動先が空のディレクトリであれば知らせずに置き換えるためである。メッセージディレクトリの `rename` が名前の重複で失敗した場合は、次の番号を付けて再試行する。展開先での例外は §12.1 に定める。
* プログラムはディレクトリ名を解釈してはならない。宛先などの値は、必ずフロントマターから読む。

### 5.3. フロントマター
`index.md` は、YAML フロントマターを含む UTF-8 の Markdown とする。書式と値の型は §5.4 に従う。システムが管理するキーには `lmm_` プレフィックスを付ける。`lmm_` で始まるキーはすべてシステムの予約とする。

**必須キー:**

| キー | 型 | 説明 |
| :--- | :--- | :--- |
| `lmm_id` | string | メッセージの一意な ID（UUID v4、小文字ハイフン区切り）。 |
| `lmm_from` | string | 送信元アドレス。 |
| `lmm_to` | string | 宛先アドレス。 |
| `lmm_created_at` | string | 作成日時。UTC の RFC 3339 形式で、秒の小数部を 6 桁（マイクロ秒）とする（例: `2026-10-05T14:30:05.123456Z`）。YAML 1.1 のパーサーでタイムスタンプ型として解釈されないよう、引用符で囲んで出力する（§5.4）。 |

**任意キー:**

| キー | 型 | 説明 |
| :--- | :--- | :--- |
| `lmm_subject` | string | 件名。 |
| `lmm_thread_id` | string | スレッド ID。1〜128 文字の任意の文字列（改行を含まない）。タスク ID など、利用者が決めた値を使える。 |
| `lmm_in_reply_to` | string | 返信元メッセージの `lmm_id`。 |
| `lmm_forwarded` | マップの配列 | 転送の履歴（§6.6）。`lmm post --forward` で送ったメッセージにだけ付く。 |

* `lmm_` で始まらないキー（例: `tags`, `task_id`）は、システムは解釈せず、そのまま保持する。ワークフロー用の情報（タスク ID、依頼の種類、ブランチ名など）は、このような独自キーで表す（§6.2 の `--meta`）。

例:
```markdown
---
lmm_id: a1b2c3d4-e5f6-4890-abcd-ef1234567890
lmm_from: alpha
lmm_to: beta
lmm_created_at: "2026-10-05T14:30:05.123456Z"
lmm_subject: Task complete
lmm_thread_id: task-042
lmm_in_reply_to: 0f9e8d7c-1111-4222-8333-444455556666
tags:
  - report
---

The analysis is complete. See ![screen](./screen.png).
```

### 5.4. フロントマターの書式と値の型
フロントマターは、人やエージェントが手で書くことがあり、ほかのツールが読むこともある。そのため、区切り方と値の型を次のように定める。

* **区切り:** `index.md` の 1 行目が `---` だけの行であれば、フロントマターがあるものとする。次に現れる `---` だけの行までをフロントマターとし、その後を本文とする。
    * 行末は LF と CRLF のどちらでもよい。先頭の UTF-8 の BOM は無視する。
    * 1 行目が `---` だけの行でなければ、フロントマターはないものとし、ファイル全体を本文とする（本文が区切り線 `---` で始まる場合と区別するため、`----` などは区切りとみなさない）。
    * 閉じの `---` の行がない場合は、解析の失敗とする。`...` は閉じの区切りとして扱わない。
* **解析:** YAML 1.2 の core schema で解析する。`yes`、`no`、`on`、`off` や、日付の形の値（`2026-10-05`）は文字列として扱う。
    * 使えるタグは、core schema の `!!str`、`!!int`、`!!float`、`!!bool`、`!!null`、`!!seq`、`!!map` と、非特定タグ `!` だけとする。それ以外のタグ（`!!binary`、`!!timestamp`、`!foo` など）は、解析の失敗とする。ほかのツールで読んだときに、同じ値になるとは限らないためである。
    * トップレベルはマップでなければならない。空のフロントマター（`---` の行が 2 行続く）は、空のマップとする。
    * キーは文字列でなければならない。同じキーが 2 回以上ある場合は、解析の失敗とする。
    * エイリアスを展開した後の内容が、次の上限を超える場合は、解析の失敗とする。エイリアスの連鎖（Billion Laughs）や深い入れ子で、メモリと時間を使い果たさないためである。
        * コレクション（マップと配列）の入れ子の深さ: 128
        * ノード（マップのキーと値、配列の要素）の数: 100,000
* **`lmm_` キーの型:** `lmm_` で始まるキーの値は、文字列でなければならない。ただし `lmm_forwarded` は、§6.6 の形のマップの配列とする。数値などとして書かれた値（例: `lmm_thread_id: 42`）は、規則に反するものとして扱う。
* **独自キー:** 値の型と、キーの順序を保つ。コメント、引用符の有無、インデントなどの書き方は保たない。
* **書き出し:** `lmm_` キーを §5.3 の表の順（必須キー、任意キーの順）に書き、独自キーを入力の順に続ける。書き出した表現が 1024 文字を超えるキーは、明示的なキーの形（`? キー` と `: 値`）で書く（YAML 1.2 の暗黙のキーは 1024 文字までのため）。文字列のうち、YAML 1.1 のパーサー（PyYAML など）では文字列以外として読まれるもの（`no`、`1.10`、`2026-10-05` など）は、引用符で囲む。ほかのツールで読んでも同じ値になるようにするためである。
* **本文:** 閉じの `---` の行より後は、バイト列としてそのまま保つ。
* **JSON への変換**（`lmm show --json`、`--field`。§7.5）: 文字列は JSON の文字列に、数値・真偽値・null・配列・マップは対応する JSON の値にする。JSON で表せない数値（`.inf`、`-.inf`、`.nan`）は、その YAML の表記を文字列として出力する。

## 6. 送信（`lmm post`）

### 6.1. コマンドインターフェース
```bash
lmm post [OPTIONS] <DIR>
```

* `DIR`: 送信者が用意したメッセージディレクトリ（`index.md` と添付ファイル）。§5.1 の規則に従っていなければエラーとする。`index.md` のフロントマターは省略してよい。受け取ったメッセージ（展開先のディレクトリ）を指定すれば、そのまま転送できる（§6.6）。転送専用のコマンドは設けない。
* 入力はメッセージディレクトリだけとする。Markdown ファイルや標準入力は受け付けない（指定した場合は、使い方の誤り（終了コード 2）とする）。入力の形を 1 つにそろえ、本文と添付ファイルを常に同じ単位で扱うためである。
* 添付ファイルは、`DIR` の中に置く。添付ファイルを個別に指定するオプションは設けない。
* 送信者が置いておくと配送される送信トレイ（outbox）は設けない。メッセージをファイルとして組み立てたい場合は、任意の場所にメッセージディレクトリを作り、`lmm post DIR` で送る。
    * outbox を設けると、常駐プロセスがないため、配送が送信者のフック（§8）の発火まで遅れる。
    * また、宛先の誤りなどが配送時まで分からず、送信者へ後から知らせる仕組み（配送不能メッセージの隔離、配送不能通知、再試行）が必要になる。`lmm post` は送信時にその場でエラーを返すため、これらを必要としない。

### 6.2. オプション

| オプション | 説明 |
| :--- | :--- |
| `-t, --to <ADDRESS>` | 宛先アドレス。指定できる宛先は 1 つだけとし、複数回指定した場合はエラーとする。1 通を複数の宛先に送る機能は設けない。複数の宛先に送る場合は、宛先ごとに `lmm post` を実行する（`lmm_id` は宛先ごとに異なる）。 |
| `-s, --subject <TEXT>` | 件名。 |
| `-r, --reply <PATH>` | 返信元のメッセージディレクトリ、またはその `index.md`。§6.5 の返信処理を行う。 |
| `--thread <ID>` | スレッド ID を明示的に指定する。§5.3 の規則に反する場合はエラーとする。 |
| `--forward` | 入力を受け取ったメッセージとして扱い、転送の履歴 `lmm_forwarded` を記録する（§6.6）。`--reply` と同時には指定できない。 |
| `-m, --meta <KEY=VALUE>` | 独自キーをフロントマターに追加する。複数回指定できる。キーは `A-Z a-z 0-9 _ . -` の文字で構成し、`lmm_` で始めてはならない。値は常に文字列として書き出す（§5.4）。 |

### 6.3. 値の決定
各値を次の優先順で決める（左が優先）。

| 項目 | 決定順 |
| :--- | :--- |
| `lmm_to` | `-t` → 返信元の `lmm_from` → 設定の `post.reply_to` → エラー |
| `lmm_subject` | `-s` → 返信元から生成（§6.5） → 入力のフロントマターの `lmm_subject` → なし |
| `lmm_thread_id` | `--thread` → 返信元から決定（§6.5） → 入力のフロントマターの `lmm_thread_id` → なし |
| `lmm_in_reply_to` | 返信元の `lmm_id` → なし |
| `lmm_id`, `lmm_from`, `lmm_created_at` | 常にシステムが生成する。`lmm_from` は `LMM_NAME` とする。 |

**フロントマターのマージ:**
* 入力の `DIR/index.md` にフロントマター（§5.4）があれば、解析する。解析に失敗した場合と、`lmm_` キーの値の型が §5.4 に反する場合は、エラーとする。入力の `lmm_thread_id` を使う場合は、§5.3 の規則にも従わなければならない。
* `lmm_` で始まるキーは、上の表で参照したものも含めてすべて破棄し、上の表で決めた値で置き換える。`lmm_forwarded` も破棄する。`--forward` を指定した場合だけ、§6.6 で決めた値を設定する。
* 独自キーは、次の順で適用する（後のものが強い）。
    1. 設定の `post.meta`（§10.4）
    2. 入力のフロントマターにある独自キー
    3. `--meta` オプション

### 6.4. 実行フロー
1. **送信元の確認:** `LMM_NAME` が未設定、またはそのメールボックスが存在しない場合はエラーとする（§3.2）。
2. **入力の読み込みと値の決定:** §6.1・§6.3 に従う。
3. **検証:** 宛先のメールボックスが存在しない場合、添付と合計サイズが §5.1 に反する場合、およびマージした `index.md` が受信時の検査（§7.3）のフロントマターの項目に合格しない場合（システムが追加したキーによって §5.4 の上限を超えた場合など）は、何も作成せずにエラー（終了コード 1）とする。
    * 宛先のメールボックスがない場合のエラーメッセージには、宛先のメールボックスがないことと、`lmm box create <アドレス>` で作成できることを含める。
    * 宛先のメールボックスを自動では作成しない。宛先の打ち間違いをその場で知らせるため、また `lmm box remove` で削除したメールボックスを遅れて届いたメールで作り直さないためである。
    * 宛先ができるまで配送を保留することもしない（常駐プロセスがないため）。
    * メールボックスは、エージェントを起動する側（tmac や flow など）が、起動前に `lmm box create <アドレス> --exist-ok` で作成することを想定している。起動前に作成しておけば、エージェントの起動より先に送られたメールも配送できる。
4. **書き込み:** 宛先の準備ロック（共有、§4.3）を取得する。宛先の `inbox/.tmp/` に作業用ディレクトリ `<UUID>/` を作成し（UUID は作業用ディレクトリごとに新たに生成する）、その中にロックファイル `lock` を作成して排他ロックを取得してから、準備ロックを解除する。続けて、`<UUID>/msg/` にメッセージディレクトリを作成し、`index.md`（フロントマターをマージしたもの）と、`DIR` の添付ファイルのコピーを書き込んで fsync する。`inbox/.tmp/` が存在しない場合はエラーとし、メールボックスのディレクトリを作成してはならない（削除されたメールボックスを作り直さないため）。
    * `lock` のロックは、書き込み中であることを示す。準備ロックは、作業用ディレクトリを作成してから `lock` のロックを取得するまでの間を保護する。どちらも、受信のたびに行う掃除（下記）が、生きている送信の作業用ディレクトリを削除しないようにするためである。
    * `msg/` のファイルは、同じ名前のファイルがあれば失敗する方法（排他的な新規作成。実装は付録 A）で作成する。名前が衝突した場合（書き込み先のファイルシステムが、§5.1 の規則で防げない別々の名前を同じファイルとみなした場合）は、エラー（終了コード 1）とする。通常のコピーでは、後からコピーしたファイルが前のファイルを上書きし、添付ファイルが欠けたり、添付ファイルで本文が置き換わったりしたまま成功するためである。
5. **公開:** 宛先のメールボックスのロック（共有、§4.3）を取得し、メールボックスがまだ存在することを確認する。`new/`、`cur/` の順に同じ名前があるかを確認し、ある場合は末尾に `_1`, `_2`, … を付けて、ディレクトリ名を決める。`inbox/.tmp/<UUID>/msg/` を `inbox/new/<ディレクトリ名>` へ、上書きしない `rename`（§5.2）で移す。`inbox/new/` を fsync してから、ロックを解除する。メールボックスが消えていた場合はエラーとする。
    * 配送どうしは共有ロックで同時に行われるため、確認してから `rename` するまでの間に、別の配送が同じ名前を使うことがある。その場合は `rename` が失敗するので、次の番号で再試行する。
    * `new/` を先に確認するのは、受信によって `new/` から `cur/` へ移る途中のメッセージを見落とさないためである。
    * `rename` の成功をもって配送の確定とする。その後の fsync が失敗しても配送は取り消さず、警告を出力して処理を続ける（§12.4）。確定後にエラーを返すと、呼び出し元の再送で同じ内容が別の ID で二重に届くためである。
6. **送信控え:** 手順 4・5 と同じ方法で、送信元の `sent/` に同じ内容を保存する。
    * 送信元の `inbox/.tmp/` に、手順 4 と同じ方法（送信元の準備ロックを使う）で作業用ディレクトリを作成し、手順 4 と同じ内容を `msg/` に書き込んで fsync する。`inbox/.tmp/` が存在しない場合は失敗とし、メールボックスのディレクトリを作成してはならない（削除されたメールボックスを作り直さないため）。
    * 送信元のメールボックスのロック（共有、§4.3）を取得し、メールボックスがまだ存在することを確認してから、`msg/` を `sent/<ディレクトリ名>` へ上書きしない `rename`（§5.2）で移す。`sent/` に同じ名前がある場合は、末尾に `_1`, `_2`, … を付ける。`sent/` を fsync してから、ロックを解除する。
    * 失敗しても配送は取り消さず、作業用ディレクトリを削除して警告を出力する。
7. **結果:** `lmm_id` と、配送したメッセージディレクトリの絶対パスを、1 つの空白で区切って標準出力に 1 行で出力する（例: `a1b2c3d4-e5f6-4890-abcd-ef1234567890 /home/u/.lmm/boxes/beta/inbox/new/20261005-143005.123456_alpha_to_beta_a1b2c3d4`）。シェルでは `read -r id path` で受け取れる（パスに空白があっても `path` に残りがすべて入る）。パスは改行を含まない（§12.6）。
    * パスは、宛先が受信すると `cur/` へ移るため使えなくなる。後から参照する場合は `lmm_id` を控え、`lmm show --id`（§7.5）や `lmm wait --in-reply-to`（§7.4）で使う。

* 作業用ディレクトリは、`msg/` を公開した後（手順 5・6）と、途中で失敗した場合に、`lock` のロックを持ったまま削除する。公開した後の削除に失敗した場合は、警告を出力するだけとする（残ったものは下記の掃除で削除される）。
* `inbox/.tmp/` に残った作業用ディレクトリは、配送・保存されていないものとして扱う。受信（§7.3）のたびに、放棄されたものを次の手順で削除する。
    1. そのメールボックスの準備ロック（排他）を、待たずに取得する。取得できなければ、準備中の送信があるため、今回の掃除は行わない（エラーにはしない）。
    2. 準備ロックを持った状態で、`inbox/.tmp/` の作業用ディレクトリのうち、`lock` の排他ロックを待たずに取得できるもの、または `lock` がないものを、放棄されたものと判定する。準備ロックを持っている間は準備中の送信がないため、生きている送信の作業用ディレクトリでは、必ずその送信が `lock` のロックを持っている。
    3. 準備ロックを解除してから、放棄された作業用ディレクトリを削除する。`lock` のロックを取得したものは、そのロックを持ったまま削除する。放棄されたものを使うプロセスはもうないため、準備ロックを解除した後に削除してよい（削除に時間がかかっても、送信の準備を待たせない）。
* 放棄の判定に経過時間を使わないのは、送信の所要時間や中断（`SIGSTOP` など）の長さに上限がなく、経過時間では生きている送信と区別できないためである（書き込み中のファイルに追記しても、ディレクトリの最終更新は変わらない）。準備ロックを使うのは、作業用ディレクトリを作成してから `lock` のロックを取得するまでの間に停止した送信を、`lock` だけでは放棄されたものと区別できないためである。
* 入力の `DIR` とその中のファイルは、変更・削除しない。
* 送信元と宛先が同じでもよい（自分宛て）。

### 6.5. 返信処理（`--reply`）
* 返信元の `index.md` のフロントマターを解析する（§5.4）。次の場合はエラーとする。
    * 解析に失敗した場合。
    * `lmm_id` と `lmm_from` のどちらかが欠けている場合。
    * `lmm_from` がアドレスの規則（§3.1）に反する場合、または `lmm_id` が UUID の形式（§5.3）でない場合。
* **件名:** 返信元に `lmm_subject` があれば、先頭に `Re: ` を付けたものとする。既に `Re: ` で始まっている場合は付けない。
* **スレッド ID:** 返信元の `lmm_thread_id` を用いる。返信元にない場合は、返信元の `lmm_id` を用いる。
* 返信元は変更・削除しない。返信元の添付ファイルは引き継がない。

### 6.6. 転送（`--forward`）
受け取ったメッセージを別の宛先へ送るには、そのメッセージディレクトリを `DIR` として `lmm post` を実行する。本文、添付ファイル、件名、スレッド ID、独自キーは、入力から引き継がれる（§6.3）。`lmm_id`、`lmm_from`、`lmm_created_at` は新たに生成される。

`--forward` を指定すると、元の送信者と、これまでに転送した参加者を `lmm_forwarded` に記録する。

* **入力の確認:** 入力のフロントマターに `lmm_id`、`lmm_from`、`lmm_to`、`lmm_created_at` がすべてなければ、エラーとする（受け取ったメッセージでないため）。
* **`lmm_forwarded` の値:** 入力の `lmm_forwarded`（なければ空の配列）の末尾に、入力のメッセージ自身を表す要素を 1 つ追加したものとする。要素は次のキーを持つマップとする。

| キー | 値 |
| :--- | :--- |
| `id` | 入力のメッセージの `lmm_id` |
| `from` | 入力のメッセージの `lmm_from` |
| `to` | 入力のメッセージの `lmm_to` |
| `created_at` | 入力のメッセージの `lmm_created_at` |

* 配列は古い順に並ぶ。先頭の要素の `from` が元の送信者、2 番目以降の要素の `from` と、このメッセージの `lmm_from` が、歴代の転送者となる。
* 入力の `lmm_forwarded` が上の形式に従っていない場合は、エラーとする。
* 要素の数が 100 を超える場合は、エラーとする（転送の繰り返しで履歴が際限なく伸びるのを防ぐため）。
* 件名に `Fwd: ` などは付けない。必要なら `-s` で指定する。
* `--forward` を指定せずに転送した場合は、`lmm_forwarded` は記録されない（入力にあっても破棄される）。

例: `alpha` が `beta` に送り、`beta` が `gamma` に、`gamma` が `delta` に転送した場合、`delta` が受け取るメッセージは次のようになる。

```yaml
lmm_id: 33333333-...
lmm_from: gamma
lmm_to: delta
lmm_forwarded:
  - id: 11111111-...        # alpha が beta に送った元のメッセージ
    from: alpha
    to: beta
    created_at: "2026-10-05T14:30:05.123456Z"
  - id: 22222222-...        # beta が gamma に転送したメッセージ
    from: beta
    to: gamma
    created_at: "2026-10-05T14:40:00.654321Z"
```

### 6.7. 下書きの作成（`lmm draft`）
```bash
lmm draft [-s <TEXT>] [--thread <ID>] [-m <KEY=VALUE>]... [DIR]
```
`lmm post` に渡すメッセージディレクトリと `index.md` を作成し、作成したディレクトリの絶対パスを標準出力に 1 行で出力する。送信者は、出力されたディレクトリの `index.md` に本文を書き、添付ファイルを置いてから、`lmm post` で送る。

```bash
d=$(lmm draft -s "Review result")
# $d/index.md に本文を書き、$d に添付ファイルを置く
lmm post -t manager "$d"
```

* **作成場所:** 下書きのディレクトリ（`index.md` を置くディレクトリ）は、次の順で最初に決まったものとする。
    1. 引数 `DIR`。指定したディレクトリを作成する。すでに存在する場合はエラーとする（既存のファイルを上書きしないため）。
    2. 下書きの置き場の中に作成する、重ならない名前のディレクトリ。名前は `{YYYYMMDD-HHMMSS}_{ランダムな 8 文字}` とする。下書きの置き場は、環境変数 `LMM_DRAFT_DIR`、設定の `draft.dir`（§10.4）、組み込みのデフォルト `.lmm-drafts/{name}` の順で最初に決まったディレクトリとする。
* 相対パスの解決とプレースホルダは、`receive.dir` と同じとする（§10.6）。親ディレクトリが存在しなければ作成する。下書きのディレクトリがデータディレクトリ（`LMM_HOME`）の中を指す場合は、エラー（終了コード 2）とする（判定は §7.2 と同じ。リンク先の存在しないシンボリックリンクを含む場合も同じエラーとする）。
* **`.gitignore`:** 引数 `DIR` の場合は `DIR`、それ以外の場合は下書きの置き場について、その親ディレクトリの名前が `.lmm-drafts` で、その中に `.gitignore` がない場合は、`*` の 1 行で作成する（§7.2 の `.lmm-inbox` と同じ理由）。例えば組み込みのデフォルトでは、下書きのディレクトリは `.lmm-drafts/<name>/<日時>_<乱数>/` となり、`.gitignore` は `.lmm-drafts/.gitignore` に作成する。
* 出力するパスが改行を含む場合は、何も作成せずにエラーとする（§12.6）。
* **`index.md` の内容:** オプションで指定した値をフロントマターに書く。`-s` は `lmm_subject`、`--thread` は `lmm_thread_id`、`-m` は独自キーとする（キーの規則は §6.2 と同じ）。`lmm post` は、入力のフロントマターのこれらの値を引き継ぐ（§6.3）。オプションを 1 つも指定しない場合は、空の `index.md` を作成する。
* 宛先（`lmm_to`）は下書きに書かない。`lmm post` は入力のフロントマターの `lmm_to` を使わないため、宛先は `lmm post` の `-t` または `--reply` で指定する。
* `LMM_NAME` が未設定の場合、`{name}` を含む下書きの置き場（組み込みのデフォルトなど）は決められないため、エラー（終了コード 2）とする。`DIR` を指定するか、`{name}` を含まない置き場を設定すれば作成できる。
* 送信後の下書きは削除しない。不要になったら利用者が削除する（`lmm post` は入力を変更・削除しない、§6.4）。

## 7. 受信（`lmm receive`）

### 7.1. コマンドインターフェース
```bash
lmm receive [--max <N>] [DIR]
```
自分の `inbox/new/` にあるメッセージを展開先へコピーし、原本を `inbox/cur/` へ移す。

* `--max <N>`: 1 回に展開する件数の上限（1 以上）。数えるのは、正常に展開した（手順 iv の `rename` が成功した）件数だけとする。省略時は上限なし。上限を超えた分は `new/` に残り、次の受信で展開される。

### 7.2. 展開先
次の順で最初に決まったものを使う。

1. 引数 `DIR`
2. 環境変数 `LMM_RECEIVE_DIR`
3. 設定の `receive.dir`（§10）
4. 組み込みのデフォルト `.lmm-inbox/{name}`

* 相対パスは、カレントディレクトリを基準に解決する。設定ファイルに書いた値は、プレースホルダ（§10.6）を展開してから解決する。
* 展開先は、データディレクトリ（`LMM_HOME`）の中を指してはならない。判定は、展開先とデータディレクトリの両方のシンボリックリンクを解決したパスで行う。展開先がまだ存在しない場合は、存在する最も近い祖先のリンクを解決して判定する。途中にリンク先の存在しないシンボリックリンクがある場合は、判定できないため、データディレクトリの中を指す場合と同じエラーとする。データディレクトリの中を指す場合は、何も作成・移動せずにエラー（終了コード 2。`lmm hook` では 1、§8.3）とする。原本を展開先と取り違えて、存在しないパスを展開済みとして出力するのを防ぐためである。
* 解決した展開先の絶対パスが改行を含む場合も、同じく何も作成・移動せずにエラーとする（§12.6）。
* 展開先のディレクトリが存在しなければ作成する（親ディレクトリも含む）。
* 展開先の親ディレクトリの名前が `.lmm-inbox` で、その中に `.gitignore` がない場合は、`*` の 1 行で作成する。ワークツリーの `git status` や `git add -A` に展開したメールが出ないようにするためである。

### 7.3. 実行フロー
1. `LMM_NAME` のメールボックスが存在することを確認してから（§3.2）、受信ロック（§4.3）を取得し、もう一度確認する。`inbox/.tmp/` に残った、放棄された作業用ディレクトリを削除する（§6.4）。
2. `inbox/new/` のメッセージディレクトリを、名前の昇順に処理する。名前は作成時刻で始まるため（§5.2）、届いているメッセージを作成時刻の順に処理することになる。作成時刻が同じ場合の順序は保証しない。正常に展開した件数が `--max` に達したら、残りは処理せずに終える。失敗したメッセージは件数に数えず、後続のメッセージの処理を続ける。1 回の呼び出しで、同じメッセージを 2 回以上試行しない。1 通ごとに、まず下記の「検査」を行い、合格したものに次を行う。
    1. 展開先に同じ名前のディレクトリがあり、その `index.md` の `lmm_id` が原本と同じ場合は、展開済みとしてコピーを省く（前回の受信が手順 iv の前で止まった場合）。
    2. 同じ名前で `lmm_id` が異なる場合（どちらかが読めない場合を含む）は、末尾に `_1`, `_2`, … を付けた名前を使う。
    3. 展開先の `.<名前>.tmp/` にコピーして fsync し、`<名前>/` へ上書きしない `rename`（§5.2）で移して、展開先のディレクトリを fsync する。コピーではシンボリックリンクをたどってはならない。ファイルは、送信と同じく排他的に新規作成する（§6.4 の手順 4）。展開先はデータディレクトリと別のファイルシステムでもよく、大文字と小文字の区別の有無が異なることがあるためである（§12.1）。`.<名前>.tmp/` が残っていれば、先に削除する。
    4. 原本を `inbox/new/` から `inbox/cur/` へ、上書きしない `rename`（§5.2）で移す。`cur/` に同じ名前がある場合は、末尾に `_1`, `_2`, … を付ける。`inbox/new/` と `inbox/cur/` を fsync する。
    5. 展開したディレクトリの絶対パスを標準出力に 1 行で出力する。
3. ロックを解除する。

* 展開先がデータディレクトリと別のファイルシステムにあってもよい。原本は常に `~/.lmm` に残る。
* 展開の保証は「少なくとも 1 回」とする。手順 iii と iv の間で停止し、さらに受信者が展開先のディレクトリを削除した場合は、次の受信で再び展開される。次の受信の展開先が前回と異なる場合も、手順 i の確認は今回の展開先しか見ないため、再び展開される。これらの重複は、手順 iii と iv の間で停止した場合に限られるため許容し、受信記録などで防ぐことはしない。この保証は展開までであり、通知（§8）には及ばない。
* 展開したメッセージの処理後の削除は、受信者が行う（例: `rm -r <パス>`）。原本（`cur/`）は削除しなくてよい。
* 手順 iv の `rename` の成功をもって、その 1 通の展開の確定とする。手順 iii・iv の `rename` の後に行うディレクトリの fsync が失敗しても、警告を出力するだけとし、展開済みとして扱う（§12.4）。
* 手順 iv の `rename` が成功する前に失敗した場合は、その 1 通の処理に失敗したものとする。失敗は、原因によって次のように扱う。1 通でも失敗した場合の終了コードは 1 とする。
    * **検査に合格しなかった**（下記）: 原本を `inbox/failed/` へ移し（下記）、残りのメッセージの処理を続ける。
    * **原本を読むときの一時的なエラー**（I/O エラー、開いているファイルが多すぎるなど）: 原本を `new/` に残してエラーログを出力し、残りのメッセージの処理を続ける。次の受信でやり直す。
    * **展開先全体の障害**（展開先のディレクトリを作成・参照できない、容量や割り当ての不足（`ENOSPC`、`EDQUOT`）、読み取り専用（`EROFS`）など）: 原本を `new/` に残し、残りのメッセージも処理せずに終える。後続のメッセージも同じ理由で失敗するためである。
    * **そのメッセージの展開先だけの失敗**（上記以外の展開先でのエラー。例: そのメッセージの `.<名前>.tmp/` を削除できない、展開先のファイルシステムが別々のファイル名を同じファイルとみなし、手順 iii の排他的な新規作成が失敗した）: 原本を `new/` に残してエラーログを出力し、残りのメッセージの処理を続ける。次の受信でやり直す。
    * 展開先のエラーでは、メッセージに原因がないため、原本を `failed/` へ移さない。
* **検査:** 原本が次のすべてを満たすことを確認する。`new/` のメッセージは公開後に書き換えられないため、検査に合格しないメッセージは、何度やり直しても合格しない。そのため、失敗回数は数えず、1 回目で `failed/` へ移す。検査の項目は、送信時の設定によらないものに限る。そのため、`lmm post` で送ったメッセージが不合格になるのは、不具合で壊れた場合に限られる（手で置いたメッセージは除く）。
    * 直下に `index.md` がある（名前の完全一致で判定する。§5.1）。
    * `index.md` のフロントマターを解析でき（§5.4）、必須キー（§5.3）がそろっている。
    * `lmm_` で始まるキーの値が、§5.4 の型に従っている。
    * `lmm_from` と `lmm_to` がアドレスの規則（§3.1）に、`lmm_id` が UUID の形式に、`lmm_created_at` が §5.3 の形式に従っている。
    * §5.1 に反するファイル（サブディレクトリ、シンボリックリンク、特殊ファイル、規則に反する名前、ASCII の大文字と小文字だけが異なる名前）がない。
    * 合計サイズ（`max_message_size`）は検査しない。サイズの上限は送信時の決まりであり、送信後に上限を下げた場合や、送信者と受信者で別の設定（`LMM_CONFIG`）を使う場合に、正しく送られたメッセージを `failed/` へ移さないためである。
* **`failed/` への移動:** 原本を `inbox/new/` から `inbox/failed/` へ上書きしない `rename`（§5.2）で移し、不合格の理由と移動先のパスをエラーログに出力する。`failed/` に同じ名前がある場合は、末尾に `_1`, `_2`, … を付ける。`failed/` のメッセージは、受信・待機・フックの対象にならない。再び受信させたい場合は、利用者が原因を取り除いて `new/` へ戻す。

### 7.4. 待機（`lmm wait`）
```bash
lmm wait [--from <ADDRESS>] [--thread <ID>] [--in-reply-to <ID>] [--meta <KEY=VALUE>]...
         [--timeout <SEC>] [--max <N>] [DIR]
```
条件に合うメッセージが自分の `inbox/new/` に届くまで待ち、届いたら展開する。flow や進行役のスクリプトが、依頼への報告を待って次の手順へ進むために使う。

| オプション | 説明 |
| :--- | :--- |
| `--from <ADDRESS>` | `lmm_from` が一致するメッセージに限る。アドレスの規則（§3.1）に反する場合は、終了コード 2 とする。 |
| `--thread <ID>` | `lmm_thread_id` が一致するメッセージに限る。 |
| `--in-reply-to <ID>` | `lmm_in_reply_to` が一致するメッセージに限る。 |
| `--meta <KEY=VALUE>` | 独自キー `KEY` の値が文字列で、`VALUE` と一致するメッセージに限る。複数回指定できる。数値や真偽値として書かれた値（例: 引用符のない `version: 1.10`）は一致しない（§5.4）。`lmm post -m` で付けた値は、常に文字列になる。 |
| `--timeout <SEC>` | 待つ時間の上限（秒）。省略時は上限なし。 |
| `--max <N>` | 1 回に展開する件数の上限。`lmm receive` と同じ（§7.1）。 |
| `DIR` | 展開先。決め方は `lmm receive` と同じ（§7.2）。 |

* **条件:** 指定した条件をすべて満たすメッセージを対象とする。条件を 1 つも指定しない場合は、すべてのメッセージを対象とする。条件を判定する前に、受信ロックを取得して §7.3 の検査を行い、不合格のメッセージは `failed/` へ移す（条件を判定できないメッセージが `new/` に残り続けないようにするため）。
* **待ち方:** `inbox/new/` を 1 秒ごとに確認する。OS のファイル監視機能（inotify、kqueue など）は使わない。OS ごとの違いを持ち込まないためである。待っている間は、ロックを持たない。
* **展開:** 対象のメッセージが 1 通以上見つかったら、その時点の対象のメッセージだけを §7.3 の手順で展開し、展開できたメッセージのパスを出力して終了する。`--max` を指定した場合は、正常に展開した件数が上限に達した時点で終える（§7.3 の手順 2）。上限に達したために処理しなかった対象のメッセージは、失敗に数えず、`new/` に残す（次の `lmm wait` や `lmm receive` で展開できる）。条件に合わないメッセージは `new/` に残す。検査で `failed/` へ移したメッセージは対象に含めない（対象がほかになければ待ち続ける）。
* **終了コード:** 次のとおりとする。
    * 0: 処理した対象のメッセージをすべて展開できた。`--max` の上限に達して、処理しなかった対象のメッセージが `new/` に残っている場合も 0 とする。
    * 1: 処理した対象のメッセージの展開に 1 通以上失敗した（§7.3。1 通も展開できなかった場合を含む）。展開できたメッセージがあれば、そのパスは出力する。条件を判定する前の検査（受信ロックの取得や `failed/` への移動）でエラーが起きた場合も 1 とする。メールボックスが存在しない場合（待っている間に削除された場合を含む）も 1 とする（§3.2）。
    * 3: 時間切れ（下記）。
    * 128 + シグナル番号: シグナルで中断した（下記。`SIGINT` なら 130、`SIGTERM` なら 143）。
* **時間切れ:** `--timeout` の時間内に対象のメッセージが届かなかった場合は、何も展開せずに終了コード 3 で終了する。
* **中断:** `SIGINT` または `SIGTERM` を受け取った場合は、展開の途中であればその 1 通を終えてから終了する。待っている間であれば、何も展開せずに終了する。どちらの場合も、終了コードは 128 + シグナル番号とし、展開できたメッセージがあればそのパスは出力する。
* **エージェントからの使用:** AI CLI のシェル実行には実行時間の上限があるため、エージェントが長時間待つ用途には向かない。エージェントが使う場合は `--timeout` を CLI の上限より短く指定し、時間切れになったら待つのをやめて作業を終える（停止する）ように指示すること。繰り返し実行して待ち続けると、そのたびにトークンとコンテキストを消費する。
* **フックとの併用:** 同じアドレスで `lmm hook` も使っている場合、フックが先に展開すると `wait` はそのメッセージを受け取れない。`wait` を使うアドレスでは `lmm hook` を使わないこと。flow などが使うアドレスは、エージェントとは別に作成することを想定している。

### 7.5. 表示（`lmm show`）
```bash
lmm show <PATH> [--json | --field <KEY>]
lmm show --id <ID> [--json | --field <KEY>]
```
メッセージを表示する。メッセージの状態は変更しない（`new/` のメッセージを表示しても展開済みにはならない）。

| オプション | 説明 |
| :--- | :--- |
| `PATH` | メッセージディレクトリ、またはその `index.md` のパス。データディレクトリの外（展開先など）でもよい。 |
| `--id <ID>` | `lmm_id` で探す。探す範囲は、`LMM_NAME` のメールボックスの `inbox/new/`、`inbox/cur/`、`inbox/failed/`、`sent/` に限る。 |
| `--json` | JSON で出力する（下記）。 |
| `--field <KEY>` | フロントマターのキー `KEY` の値だけを出力する（下記）。 |

* `PATH` と `--id` はどちらか一方を指定する。両方、またはどちらも指定しない場合は、使い方の誤り（終了コード 2）とする。ID かパスかを引数の形から推測しないのは、ID と同じ名前のファイルがあったときに取り違えないためである。
* `--json` と `--field` は同時に指定できない。
* **出力（既定）:** `index.md` の内容をそのまま出力する。
* **出力（`--json`）:** 次のキーを持つ JSON オブジェクトを 1 つ出力する。

| キー | 値 |
| :--- | :--- |
| `path` | メッセージディレクトリの絶対パス |
| `frontmatter` | フロントマター全体（独自キーを含む）。値は §5.4 の規則で JSON に変換する |
| `body` | 本文（フロントマターを除いた部分） |
| `attachments` | 添付ファイル名の配列（名前の昇順） |

* **出力（`--field`）:** 値が文字列の場合は、そのまま出力する（改行を含む文字列は複数行になる）。文字列以外（数値、真偽値、null、配列、マップ）は、§5.4 の規則で JSON に変換し、1 行で出力する。キーがない場合は、何も出力せずに終了コード 1 とする。
* **`--id` の検索:** 索引は持たず、各メッセージの `index.md` のフロントマターを読んで探す。ディレクトリ名は解釈しない（§5.2）。`index.md` がない、またはフロントマターを解析できない候補は、警告を出力して飛ばし、検索を続ける（`failed/` には、そのようなメッセージがあり得るため）。見つからない場合は終了コード 1 とする。複数見つかった場合（自分宛てのメッセージは `inbox` と `sent/` の両方にある）は、`inbox/new/`、`inbox/cur/`、`inbox/failed/`、`sent/` の順で最初に見つかったものを使う。
* 他人のメールボックスは探さない。アドレスごとにメールボックスを分けた意味をなくさないためである。
* `PATH` で指定したメッセージ、または `--id` で見つかったメッセージについて、`index.md` がない、またはフロントマターを解析できない場合は、終了コード 1 とする。

## 8. フック（`lmm hook`）

### 8.1. 目的
AI CLI のフック（例: Claude Code の `Stop`）から呼び出し、新着があればエージェントに知らせる。`lmm receive` を実行し、1 通以上展開した場合だけ通知コマンドを実行する。

### 8.2. コマンドインターフェース
```bash
lmm hook [DIR]
```
`DIR` の意味と決め方は `lmm receive` と同じ（§7.2）。

### 8.3. 実行フロー
1. `LMM_NAME` が未設定の場合は、何もせずに終了コード 0 で終了する。LMM に参加していないセッションでも、同じフック設定を共有できるようにするためである。`LMM_NAME` のメールボックスが存在しない場合は、警告を出力して終了コード 0 で終了する。タスクの終了時にメールボックスを削除した後も、エージェントのセッションが残っていることがあり、停止のたびにエラーを出さないためである。
2. 受信ロックを取得する前に、`inbox/new/` が空かを確認する。空なら、何も出力せずに終了コード 0 で終了する。フックは停止のたびに呼ばれるため、新着がないときの処理を一覧の取得だけにする。
3. §7.3 の受信を、設定の `hook.max_messages` を `--max` として行う。手順 2 の確認はロックを持たずに行ったため、§7.3 の手順に従って、ロックを取得した後に改めて `new/` を読む（§4.3）。展開したメッセージが 0 通なら、何も出力せずに終了する（受信でエラーがなければ終了コード 0）。
    * 展開したパスは、§7.3 の手順 v と異なり標準出力に出さず、内部で集めて手順 4 で使う。`lmm hook` の標準出力に書くのは、通知コマンドと組み込みの出力だけである（§12.6）。パスの行の後に通知コマンドの JSON が続くと、AI CLI が JSON として解釈できなくなるためである。
4. 通知コマンドを実行する。通知コマンドは、次の順で最初に決まったものとする。
    1. 環境変数 `LMM_HOOK_CMD`
    2. 設定の `hook.cmd`
    3. なければ、組み込みの出力（展開したパスの一覧と、読んで対応するよう促す文）を標準出力に出す。

* **組み込みの出力の対象:** 組み込みの出力は、フックの標準出力をエージェントの文脈に加えるイベント（例: Claude Code の `UserPromptSubmit`、`SessionStart`）向けである。Claude Code の `Stop` フックでは、終了コード 0 の通常の標準出力はエージェントに渡らない。そのため `Stop` フックで使う場合は、`hook.cmd` で JSON を出力させる（§11）。組み込みの出力のまま `Stop` フックで使うと、メッセージは展開済みになるが、エージェントには通知されない（§8.5）。

* **終了コード:** 通知コマンドを実行した場合は、その終了コードを返す（§8.4）。組み込みの出力を出した場合は、受信で一部のメッセージの展開に失敗していても 0 を返す（失敗はエラーログとして標準エラー出力に出す）。それ以外の場合、`lmm hook` が返す終了コードは 0 と 1 だけとする（通知コマンドの実行中のシグナルによる中断を除く。§8.4）。使い方の誤りや設定エラー（§12.5 では 2）も、原因によらず 1 とする。
    * 組み込みの出力で 0 を返すのは、組み込みの出力の対象のイベント（例: Claude Code の `UserPromptSubmit`、`SessionStart`）では、終了コードが 0 以外だと標準出力がエージェントの文脈に加わらないためである。1 を返すと、正常に展開できたメッセージも通知されないまま `cur/` へ移る。
    * AI CLI によっては、フックの終了コード 2 に特別な意味がある。例えば Claude Code の `Stop` フックでは、2 は「停止させずに会話を続ける」ことを表し、標準エラー出力が続ける理由としてエージェントに渡される。設定の誤りは直すまで毎回起きるため、2 を返すと、エージェントは停止しようとするたびに続行させられ、§8.5 の「無限に継続させることはない」が成り立たなくなる。
    * 1 であれば、Claude Code はエージェントを止めずに、エラーを利用者に表示する。

### 8.4. 通知コマンドの実行
* `/bin/sh -c <コマンド文字列>` で実行する。カレントディレクトリは `lmm hook` のカレントディレクトリとする。
* 標準入力は `lmm hook` の標準入力をそのまま渡す（AI CLI がフックに渡す JSON を通知コマンドで読めるようにするため）。
* 標準出力・標準エラー出力も `lmm hook` のものをそのまま使い、終了コードもそのまま `lmm hook` の終了コードとする。AI CLI ごとの出力形式（例: Claude Code の `{"decision": "block", "reason": "..."}`）と終了コードの意味は、通知コマンドの側で合わせる。`lmm hook` 自身が返す終了コードは、0 と 1 だけである（§8.3。シグナルによる中断を除く、下記）。
* 通知コマンドは、新しいプロセスグループで起動する。実行時間が設定の `hook.timeout` を超えた場合は、プロセスグループ全体に `SIGTERM` を送り、2 秒たっても終了しなければ `SIGKILL` を送る。その後、エラーを出力して終了コード 1 とする。
    * `/bin/sh` のプロセスだけを終了させると、`sh` が起動した子プロセスが標準出力を開いたまま残る。AI CLI は標準出力が閉じるまでフックの終了を待つため、タイムアウトが効かなくなる。
* 通知コマンドの実行中に `lmm hook` が `SIGTERM`、`SIGINT`、`SIGHUP` を受け取った場合は、同じシグナルを通知コマンドのプロセスグループ全体に送る。通知コマンドが終了するのを、`hook.timeout` の残りの時間と 2 秒のうち短い方だけ待ち、終了しなければ `SIGKILL` を送る。その後、128 + シグナル番号を終了コードとして終了する。
    * 通知コマンドは別のプロセスグループで動くため、AI CLI が自分のタイムアウトなどで `lmm hook` を終了させても、そのままでは通知コマンドに届かず、残り続けるためである。
    * `SIGKILL` は捕捉できないため転送できない。`lmm hook` が `SIGKILL` で終了した場合、通知コマンドは残り得る。
* 環境変数は、`lmm hook` の環境変数に次の変数を追加したものとする。

| 環境変数 | 値 |
| :--- | :--- |
| `LMM_NAME` | 受信者のアドレス |
| `LMM_RECEIVE_DIR` | 展開先の絶対パス |
| `LMM_RECEIVED` | 展開したメッセージディレクトリの絶対パスを、改行で区切った一覧（パスは改行を含まない。§12.6） |
| `LMM_RECEIVED_COUNT` | 展開した件数 |
| `LMM_PENDING_COUNT` | 上限により展開せず、`new/` に残っている件数 |

* メッセージの値（件名など）は渡さない。必要な場合は、通知コマンドの中で `index.md` を読む。
* `LMM_RECEIVED` の長さは、`hook.max_messages` の上限（§10.4）により、1 つの環境変数の上限（Linux では 128 KiB）を超えない。
* 通知コマンドが失敗しても、メッセージは展開済み（`cur/`）のままとし、再通知しない。展開先には残っているので、エージェントが展開先を見れば読める。

### 8.5. 再通知
展開済みのメッセージは `cur/` にあるため、フックが何度発火しても再通知しない。新着がなければ `lmm hook` は何も出力せず、`lmm hook` 自身のエラーでも終了コード 2 を返さない（§8.3）。そのため、`Stop` フックで使っても無限に継続させることはない。

`hook.max_messages` を超えた分は `new/` に残り、次にフックが発火したときに展開・通知される。エージェントが一度に大量のメッセージを渡されることもない。

通知は「最大 1 回」とする。原本を `cur/` へ移してから通知コマンドを実行するまでの間に停止した場合、または通知コマンドが失敗した場合、そのメッセージは通知されない（展開先には残る）。

## 9. メールボックスの管理（`lmm box`）

### 9.1. `lmm box create <ADDRESS>`
メールボックスのロック（排他、§4.3）を取得し、メールボックスを作成する。すでに存在する場合はエラーとする（`--exist-ok` で成功扱い）。アドレスが §3.1 に反する場合は、終了コード 2 とする。

作成は次の手順で行い、途中で停止しても中途半端なメールボックスが見えないようにする。

1. `boxes/.creating/<アドレス>/` と `boxes/.removing/<アドレス>/` が残っていれば、削除する（前回の作成・削除が途中で停止した場合）。
2. `boxes/.creating/<アドレス>/` に §4.2 の構成をすべて作成し、fsync する。
3. `boxes/.creating/<アドレス>/` を `boxes/<アドレス>` へ、上書きしない `rename`（§5.2）で移し、`boxes/` を fsync する。

* 手順 3 の `rename` の成功をもって、作成の確定とする。
* `.creating/` と `.removing/` は、存在しなければ作成する（§9.3 でも同じ）。
* `.creating/` と `.removing/` の下には、アドレスと同じ名前のディレクトリを置く。同じアドレスの作成・削除しか使わず、どちらもメールボックスのロックを持って操作するため、ほかの処理と衝突しない。

### 9.2. `lmm box list`
メールボックスの一覧と、`new/` と `failed/` の件数を表示する。`boxes/` 直下の `.` で始まるディレクトリ（作業用、§4.2）は表示しない。

### 9.3. `lmm box remove <ADDRESS>`
アドレスが §3.1 に反する場合は、何もせずに終了コード 2 とする（例えば `..` を受け付けると、下記の手順 1 が `boxes/.removing/..`、つまり `boxes/` 全体を削除するため）。

受信ロック、メールボックスのロックの順に排他で取得する（§4.3）。ロックを持った状態で、`inbox/new/` が空であることと、`inbox/.tmp/` に書き込み中の作業用ディレクトリ（`lock` の排他ロックを待たずに取得できないもの、§6.4）がないことを確認する。満たさない場合は、`--force` がない限りエラーとする。ロックファイル（`locks/`）は削除しない。

* 放棄された作業用ディレクトリは、メールボックスと一緒に削除する。異常終了した送信の残骸があるだけで、`--force` が必要にならないようにするためである。
* 準備ロック（§4.3）は取得しない。準備中でまだ `lock` のロックを取得していない送信を放棄されたものとみなしても、メールボックスを削除する場合は、その送信は公開の時点でメールボックスがないことを確認して失敗する（下記）ため、結果が変わらない。

削除は次の手順で行い、途中で停止しても中途半端なメールボックスが見えないようにする。ロックは手順 3 を終えるまで持ち続ける。

1. `boxes/.removing/<アドレス>/` が残っていれば、削除する。
2. `boxes/<アドレス>` を `boxes/.removing/<アドレス>` へ、上書きしない `rename`（§5.2）で移し、`boxes/` を fsync する。
3. `boxes/.removing/<アドレス>/` を削除する。

* 手順 2 の `rename` の成功をもって、削除の確定とする。手順 3 が失敗した場合は、警告を出力して成功とする。残ったものは、同じアドレスの次の作成か削除が削除する（§9.1）。
* メールボックスが存在しない場合も、受信ロックとメールボックスのロックを取得し、`boxes/.removing/<アドレス>/` が残っていれば削除して、終了コード 0 とする（前回の削除を完了させたものとみなす）。残っていなければ、メールボックスが存在しないエラー（終了コード 1）とする。

`cur/` と `sent/` は自動では削除せず、古いものだけを削除するコマンドも設けない。不要になったメールボックスは、`lmm box remove` で履歴ごと削除する。タスクごとに作るメールボックスは、タスクの終了時に削除することを想定している。

ロックを持っている間は配送の公開（§6.4 の手順 5）が行われないので、空であることを確認した後に届いたメッセージが一緒に削除されることはない。書き込み途中だった送信（§6.4 の手順 4）と送信控え（手順 6）は、公開の時点でメールボックスがないことを確認して失敗する。

## 10. 設定（階層型）

各コマンドの既定値は、グローバルの設定ファイルと、ディレクトリ階層に置いた設定ファイルを重ね合わせて決める。手元（カレントディレクトリに近い側）の設定ほど優先する。

### 10.1. 設定ファイルの種類

| 種類 | 場所 | 用途 |
| :--- | :--- | :--- |
| グローバル | `$LMM_CONFIG`。未設定なら `$LMM_HOME/config.yml`（`~/.lmm/config.yml`） | 利用者全体の既定値 |
| 共有 | 各ディレクトリの `.lmm.yml` | リポジトリにコミットして共有する設定 |
| 個人 | 各ディレクトリの `.lmm.local.yml` | その場所だけの個人設定。git の対象外にすること |

* `LMM_CONFIG` で指定したファイルが存在しない場合はエラーとする。既定の場所に存在しない場合は、グローバル設定なしとして扱う。
* ホームディレクトリの `~/.lmm.yml` と `~/.lmm.local.yml` は、グローバル設定ではなく、ホームディレクトリに置いた共有・個人設定として扱う。
* ディレクトリ側の個人設定を `.lmm/config.yml` にしないのは、ホームディレクトリではグローバル設定（`~/.lmm/config.yml`）と同じパスになるためである。
* 形式は YAML とする。すべての項目は省略できる。

### 10.2. 探索と優先順位
カレントディレクトリから親ディレクトリへ順にたどり、ファイルシステムのルートまでの各ディレクトリで `.lmm.local.yml` と `.lmm.yml` を探す。値は次の順で強いものが優先する（上ほど強い）。

1. コマンドラインのオプション・引数
2. 環境変数（§10.5 の表）
3. カレントディレクトリの `.lmm.local.yml`
4. カレントディレクトリの `.lmm.yml`
5. 親ディレクトリの `.lmm.local.yml`、`.lmm.yml`（以下、ルートに向かって同様）
6. グローバル設定
7. 組み込みのデフォルト値

* ディレクトリ側の設定ファイルに `root: true` がある場合、そのディレクトリより上の親は探索しない。同じディレクトリのもう一方のファイルと、グローバル設定は引き続き適用する。
* 読み取り権限のないディレクトリやファイルは、警告を出力して飛ばす。

### 10.3. 値の合成
* スカラー値（文字列・数値・真偽値）と配列は、強い側の値で丸ごと置き換える。
* マップ（例: `post.meta`）は、キーごとに合成する。同じキーは強い側の値とする。
* `null` は値として書けない。書いた場合は、その設定ファイルの設定エラーとする。
* 未知のキーは、警告を出力して無視する。

### 10.4. 設定項目

| キー | 型 | 組み込みのデフォルト | 説明 |
| :--- | :--- | :--- | :--- |
| `root` | boolean | `false` | §10.2 の探索の打ち切り。合成の対象ではなく、そのファイルにだけ効く。グローバル設定に書いた場合は無視する。 |
| `receive.dir` | string | `.lmm-inbox/{name}` | 展開先（§7.2）。 |
| `draft.dir` | string | `.lmm-drafts/{name}` | `lmm draft` が下書きを作成するディレクトリ（§6.7）。 |
| `hook.cmd` | string | なし（組み込みの出力） | 通知コマンド（§8.3）。 |
| `hook.timeout` | 数値（秒） | `30` | 通知コマンドの実行時間の上限。0 より大きい値とする。 |
| `hook.max_messages` | 整数 | `20` | `lmm hook` が 1 回に展開・通知する件数の上限（§8.3）。1〜30 とする。パスの長さが最大（4096 バイト）でも、`LMM_RECEIVED` が 1 つの環境変数の上限（Linux では 128 KiB）を超えないようにするためである。 |
| `post.reply_to` | string | なし | `lmm post` で宛先を省略したときの宛先。アドレスの規則（§3.1）に従う。 |
| `post.meta` | マップ（キー・値とも文字列） | なし | `lmm post` が毎回付ける独自キー。キーの規則は `--meta` と同じ（§6.2）。値が文字列でない場合は設定エラーとする（数値なども引用符で囲む）。`--meta` と同じく、値は常に文字列として書き出す。 |
| `max_message_size` | 数値（バイト）または単位付き文字列（`K`, `M`, `G`。1024 倍単位） | `1G` | 1 通あたりの合計サイズの上限（§5.1）。グローバル設定でのみ有効とし、ディレクトリ側に書いた場合は警告を出力して無視する。 |

### 10.5. 環境変数

| 環境変数 | 対応する設定 | 備考 |
| :--- | :--- | :--- |
| `LMM_HOME` | — | データディレクトリ（§4.1）。設定ファイルでは変更できない。 |
| `LMM_NAME` | — | 自分のアドレス（§3.2）。設定ファイルでは指定できない。 |
| `LMM_CONFIG` | — | グローバル設定ファイルのパス。 |
| `LMM_RECEIVE_DIR` | `receive.dir` | |
| `LMM_DRAFT_DIR` | `draft.dir` | |
| `LMM_HOOK_CMD` | `hook.cmd` | |

### 10.6. パスとプレースホルダ
* 文字列の値では、次のプレースホルダを使える。`{` を文字として書く場合は `{{` とする。未知のプレースホルダは設定エラーとする。

| プレースホルダ | 値 |
| :--- | :--- |
| `{name}` | `LMM_NAME` の値 |
| `{cwd}` | カレントディレクトリ |
| `{config_dir}` | その値を書いた設定ファイルがあるディレクトリ |

* `hook.cmd` ではプレースホルダを展開しない。通知コマンドは、環境変数（§8.4）で値を受け取る。
* パスを表す値（`receive.dir`、`draft.dir`）は、プレースホルダの展開後、先頭の `~/` をホームディレクトリに展開する。相対パスの場合は、カレントディレクトリを基準に解決する。

例（リポジトリ直下の `.lmm.yml`。Claude Code の `Stop` フックで使う場合、§11）。サブディレクトリで起動したエージェントの展開先も、リポジトリ直下にまとまる。
```yaml
root: true
receive:
  dir: "{config_dir}/.lmm-inbox/{name}"
hook:
  cmd: >-
    jq -n --arg paths "$LMM_RECEIVED"
    '{decision: "block", reason: ("新着メッセージがあります。次のディレクトリの index.md を読んで対応し、処理後に削除してください:\n" + $paths)}'
post:
  meta:
    project: myrepo
```

### 10.7. `lmm config show`
```bash
lmm config show [-C <DIR>] [--origin]
```
起点ディレクトリで有効になる設定を、合成後の YAML として表示する。読み込んだ設定ファイルの一覧（優先順）も、先頭にコメントとして表示する。

| オプション | 説明 |
| :--- | :--- |
| `-C <DIR>` | 起点ディレクトリ。省略時はカレントディレクトリ。 |
| `--origin` | 各値の後ろに、その値を定義した場所（設定ファイルのパス、環境変数名、組み込みの場合は `(default)`）をコメントとして付ける。 |

## 11. 使い方の例（Claude Code）

```bash
# エージェントの起動前（tmac などが行う）
lmm box create reviewer --exist-ok
export LMM_NAME=reviewer
```

`.claude/settings.json` の `Stop` フックに `lmm hook` を登録する。

```json
{
  "hooks": {
    "Stop": [
      { "hooks": [{ "type": "command", "command": "lmm hook" }] }
    ]
  }
}
```

`hook.cmd`（§10.6 の例）で、`{"decision": "block", "reason": "..."}` を出力させる。新着があればエージェントは停止せずにメールを読み、新着がなければ通常どおり停止する。

* `hook.cmd` は必ず設定する。`Stop` フックでは、終了コード 0 の通常の標準出力はエージェントに渡らないため、組み込みの出力のままでは通知が届かない（§8.3）。
* JSON は `jq` で組み立てる。`LMM_RECEIVED` の値（パスに含まれ得る `"` や `\`、パスを区切る改行）を、`printf` などで正しくエスケープするのは難しいためである。§10.6 の例は、引用符や `\` を含むパスでも正しい JSON を出力する。
* `lmm hook` 自身の警告やエラーは標準エラー出力に出るので（§12.6）、標準出力の JSON を壊さない。

## 12. 非機能要件

### 12.1. 動作環境
* 単一ユーザーのローカル開発環境で使うことを想定する。複数のユーザーが使う共有マシンは対象外とする。
* Linux と macOS を対象とする。`/bin/sh` を必要とする。
* データディレクトリは、`flock(2)` と上書きしない `rename`（§5.2）が正しく動作するローカルファイルシステム上に置く（§4.1）。展開先のファイルシステムが上書きしない `rename` に対応していない場合（`EINVAL` などで失敗する場合）は、展開先でだけ通常の `rename` を使う。展開先の名前は、受信ロックを持った状態で §7.3 の手順 i・ii によって確認済みのためである。
* データディレクトリと展開先は、大文字と小文字を区別しないファイルシステム上にあってもよく、両者で区別の有無が異なってもよい（例: コンテナの中のデータディレクトリと、macOS からバインドマウントしたワークツリーの中の展開先）。ファイル名の規則（§5.1）と、コピーの際の排他的な新規作成（§6.4、§7.3）によって、名前の同一視による上書きを防ぐ。

### 12.2. リソース
* 常駐プロセスを持たない。
* `lmm hook` は新着がない場合、`inbox/new/` の一覧を取るだけで終了する（§8.3 の手順 2）。

### 12.3. セキュリティ
* 同一ユーザーの参加者は、互いに信頼できるものとみなす。ただし、メッセージの内容（件名や本文など）は信頼できない入力として扱う。
* メッセージの値をシェルコマンド文字列に埋め込んではならない。通知コマンドには、値を環境変数で渡す（§8.4）。
* メッセージディレクトリの中にシンボリックリンクを置くことは禁止し（§5.1）、コピーと検証ではシンボリックリンクをたどらない（§6.4、§7.3）。
* 展開先にデータディレクトリの中は指定できない（§7.2）。
* 作成するファイルとディレクトリのパーミッションは、umask に従う。

### 12.4. 永続性
* 本書が保証するのは、次の 2 点である。
    * 配送が確定した（§6.4 の手順 5 の `rename` が成功した）メッセージの原本は、メールボックスの明示的な削除（`lmm box remove`、§9.3）を除き、プロセスの異常終了によって失われない。
    * 確定したメッセージのうち、受信時の検査（§7.3）に合格したものは、少なくとも 1 回展開される。不合格のものは展開されず、原本は `failed/` に残る。
* 重複は排除しない。送信の確定後に結果を返す前に停止して再送した場合（別の ID で届く）と、§7.3 の再展開は、重複になり得る。
* これらの保証は、**プロセスの異常終了**（シグナルによる終了、強制終了など）を対象とする。
* 配送と展開の確定点は `rename` の成功とする。その後のディレクトリの fsync の失敗は、警告として扱う（§6.4、§7.3）。
* OS のクラッシュや電源断に対しては、保証しない。§6.4・§7.3・§9 で行うファイルとディレクトリの fsync は、被害を減らすための努力目標とする。

### 12.5. 終了コード

| コード | 意味 |
| :--- | :--- |
| 0 | 成功 |
| 1 | 実行時エラー（宛先なし、ロックの取得失敗、ファイル I/O エラーなど） |
| 2 | 使い方の誤りまたは設定エラー（不正なオプション、不正なアドレス、設定ファイルの不正など） |
| 3 | 時間切れ（`lmm wait` の `--timeout`、§7.4） |
| 128 + シグナル番号 | シグナルによる中断（`lmm wait`、§7.4。`lmm hook` の通知コマンドの実行中、§8.4） |

`lmm hook` は、通知コマンドを実行した場合、その終了コードを返す（§8.4）。通知コマンドの実行中にシグナルで中断した場合は 128 + シグナル番号を返す（§8.4）。それ以外の場合は 0 か 1 だけを返し、使い方の誤りや設定エラーでも 2 を返さない（§8.3）。

### 12.6. 標準出力と標準エラー出力
* 標準出力には、各コマンドで定めた結果だけを出す。例えば、`lmm post` の ID とパス（§6.4）、`lmm draft` の作成したパス（§6.7）、`lmm receive`・`lmm wait` の展開したパス（§7.3）、`lmm show` の出力（§7.5）、`lmm hook` の組み込みの出力（§8.3）である。`lmm hook` は、受信で展開したパスを標準出力に出さない（§8.3 の手順 3）。
* パスは 1 行に 1 つ出力し、`LMM_RECEIVED`（§8.4）でも改行で区切るため、改行を含むパスは扱わない。次のパスが改行を含む場合は、状態を変更する前に、使い方の誤りまたは設定エラー（終了コード 2。`lmm hook` では 1、§8.3）とする。
    * `lmm post`: データディレクトリ（`LMM_HOME`）の絶対パス。
    * `lmm draft`: 作成する下書きのディレクトリの絶対パス（§6.7）。
    * `lmm receive`、`lmm wait`、`lmm hook`: 展開先の絶対パス（§7.2）。相対パスは、カレントディレクトリを基準に解決した後のパスで判定する。
    * メッセージディレクトリの名前（§5.2）は、アドレスの規則（§3.1）などにより改行を含まないため、判定するのはこれらの基準のパスだけでよい。
* 警告、エラー、エラーログは、すべて標準エラー出力に出す。本書で「警告を出力する」「エラーログに出力する」としているものも、標準エラー出力に出す。
* 標準出力は、`read -r id path` やフックの JSON のように、プログラムが読むためである。警告が 1 行でも混ざると、ID とパスを取り違えたり、AI CLI が JSON として解釈できなくなったりする（Claude Code は、標準出力全体が 1 つの JSON オブジェクトのときだけ JSON として扱う）。

## 付録 A. 実装の注記（Rust）

本書の振る舞いを Rust で実装するときの対応を示す。仕様の一部ではなく、実装の参考である。

| 本書の規定 | Rust での実装 |
| :--- | :--- |
| ロック（§4.3） | `std::fs::File::lock` と `lock_shared` を使う（Rust 1.89 以降。Linux と macOS では `flock(2)` を呼ぶ）。待ち時間の上限（10 秒）を指定する機能は標準ライブラリにないため、`try_lock` と `try_lock_shared` を一定の間隔で繰り返す。掃除が準備ロックを取得する場合と、送信以外が作業用ディレクトリの `lock`（§6.4）のロックを取得する場合は、`try_lock` を 1 回だけ呼ぶ。 |
| 排他的な新規作成（§6.4、§7.3） | `std::fs::copy` は移動先のファイルを上書きするため使わない。`OpenOptions` の `create_new(true)`（`O_CREAT` と `O_EXCL`）で開いてから内容を書き込む。ファイルシステムが同じファイルとみなす名前のファイルが既にあれば、`ErrorKind::AlreadyExists` で失敗する。 |
| 上書きしない `rename`（§5.2） | `std::fs::rename` は移動先を置き換えるため使わない。Linux では `renameat2(2)` の `RENAME_NOREPLACE`、macOS では `renamex_np(2)` の `RENAME_EXCL` を、rustix か libc を通して呼ぶ。対応していないファイルシステムでは `EINVAL` などで失敗する（§12.1）。 |
| fsync（§6.4、§7.3、§9） | `File::sync_all` を使う。macOS では `fsync(2)` ではなく `F_FULLFSYNC` を使うので、ディスクへの書き込みまで要求できる。ディレクトリは、ディレクトリを開いた `File` に対して呼ぶ。 |
| 通知コマンドのプロセスグループ（§8.4） | `std::os::unix::process::CommandExt::process_group(0)` で起動する。タイムアウトしたら、プロセスグループにシグナルを送る（`kill(2)` に負の PID を渡す）。`lmm hook` が受け取ったシグナルの転送は、`signal-hook` でシグナルを記録し、待機のループの中でプロセスグループへ送る。 |
| フロントマター（§5.4） | YAML 1.2 の core schema に従うクレートを使う。`no` が文字列として読まれること、キーの重複がエラーになること、紛らわしい文字列を引用符で囲んで書き出すことを、テストで確かめる。 |
